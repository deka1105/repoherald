# repoherald

Portal where people/companies post GitHub repos for discovery and starring. Verified stars mint credits (1 credit = 1h self-highlight or 15min donated highlight). Sponsored repos get pinned/injected feed placement. Admin portal manages sponsorships, credits, moderation.

## Commands

- `npm run dev` — dev server (http://localhost:3000)
- `npm run build` — production build
- `npm run lint` — ESLint
- `npx tsc --noEmit` — type-check
- `npx drizzle-kit generate` — generate SQL migration from `src/db/schema.ts`
- `npx drizzle-kit migrate` — apply migrations (needs `DATABASE_URL`)

- `npm run test:mobile-auth` / `npm run test:resolve` / `npm run test:nemotron` /
  `npm run test:analytics` / `npm run test:seo` / `npm run test:username` —
  plain `tsx` scripts, 373 assertions, no framework, no database, no API key and
  no internet required (`test:nemotron` runs the client against a local server
  speaking Token Factory's shapes, so the retry rules are proved not assumed).
  `test:analytics` and `test:seo` pass `--conditions=react-server` so
  `server-only` resolves to its empty build instead of throwing — that is how to
  test a module that is marked `server-only`, rather than unmarking it.
- `npm run nemotron:doctor` — is Nebius reachable and are the model ids real?
- `npm run eval:resolve -- --limit 20` — identification accuracy; **spends tokens**

## Architecture

- **Stack:** Next.js App Router (TS), Clerk for identity (see **Auth** below), Neon Postgres + Drizzle (`drizzle-orm/neon-serverless` WebSocket driver — chosen over neon-http because the credit ledger needs interactive transactions with `SELECT ... FOR UPDATE`), Tailwind v4 + shadcn/ui, Stripe Checkout, Vercel Cron.
- **Auth:** Clerk, with the Google and GitHub connections configured in the Clerk dashboard rather than in env. `src/auth.ts` wraps Clerk's `auth()` and resolves it to a row in `users` via `src/lib/clerk-user.ts`: Clerk owns identity, that table still owns role, credits, mint eligibility and claimed handles. An account predating Clerk is adopted on first sign-in by **verified** email only (`src/lib/account-link.ts`) — an unverified address would let anyone who can type it walk into the account that owns it. Middleware is `src/proxy.ts` (Next 16 renamed `middleware.ts`) and deliberately does **not** gate routes; authorisation is per-page and per-action via `requireUser`/`requireModerator`/`requireAdmin`, which need the DB for roles. GitHub tokens come from `src/lib/github-token.ts`, which reads Clerk first and falls back to a locally encrypted token. **The iOS app signs in through Clerk too** (`@clerk/expo`), so both platforms share one identity: it posts a Clerk session token to `/api/mobile/v1/session`, which verifies it with `@clerk/backend` and exchanges it for the 30-day bearer token in `src/lib/mobile-auth.ts` (a Clerk token lives ~1 minute and throws offline, so it proves identity once rather than authenticating every call). The encrypted-token fallback is now historical — it serves only accounts created by the earlier build that ran its own GitHub OAuth. Mobile sign-in going through Clerk is also what satisfies App Store Guideline 4.8: Sign in with Apple is a Clerk dashboard connection rather than a second OAuth client. **Admins** come from two env lists, never from a signup: `ADMIN_GITHUB_LOGINS` (unreachable for a Google-only account, which has no login) and `ADMIN_EMAILS` — *primary* admins, granted on every sign-in with that **verified** address and refused by `setUserRole`, so no admin can demote the operator. Changing who is a primary admin is an env change plus a redeploy, deliberately: a DB write must not be able to grant admin.
- **Usernames** (`src/lib/username.ts` for the rules, `src/lib/username-claim.ts` for the table): every account carries a unique public handle, which is what the chrome, the feed's compose row and comment bylines now address people by — `github_login` is null for a Google-only account, so it could never be that. Assigned on sign-in, not by a webhook, for the same reason `resolveClerkUser` is on the request path: there must be no window in which somebody is signed in without one. It is **seeded from the GitHub login where that login survives the rules**, and only generated (`silent-otter`, then `silent-otter-4821`) otherwise — assigning a random pair to an account GitHub already names would rename that person at sign-up. Stored **lowercase**, which is what makes the plain `UNIQUE` constraint case-insensitive without citext; `normaliseUsername` is therefore load-bearing, not cosmetic, and both the check and the write must go through it. Uniqueness is decided by the index, never by a `SELECT` first: `setUsername` translates a 23505 back into "already taken", because a check-then-write lets two simultaneous claims both pass. `ensureUsername`'s every update carries `AND username IS NULL` so concurrent sign-ins cannot overwrite each other, and its candidate ladder ends in `member-<id>`, which cannot collide — that is why the loop terminates. The reserved list covers route segments (so a future `/u/<handle>` cannot be shadowed) plus anything reading as staff or as the site; `deleted-` and `member-` are reserved as prefixes because the system writes them itself. The column is **nullable although nothing should leave it null** — a handle that could not be generated is cosmetic, not a reason to refuse a sign-in, so every read coalesces (`src/lib/display-name.ts`). `purgeAccount` overwrites the handle with `deleted-<full id>` rather than clearing it: releasing it would let the next person claim the name a deleted account's bylines still carry, and the *full* id is used because `username` is UNIQUE where `github_login` is not, so a prefix collision would make a deletion fail permanently.
- **Schema:** `src/db/schema.ts`. Key invariants: `star_mints` is permanent (revoked rows still block re-minting via `UNIQUE (user_id, repo_id)`); `credit_entries` is an append-only ledger and the source of truth for `users.credit_balance` (cache, may go negative); partial unique indexes allow one `mint` and one `revocation_clawback` per star.
- **Credit mutations** all go through `src/lib/credits.ts`, each a single transaction locking the user row.
- **GitHub API:** `src/lib/github.ts` — star verification uses the starring user's own token (`GET /user/starred/{owner}/{repo}`), scopes `read:user user:email` only.
- **Highlight status** is always derived from `starts_at`/`ends_at` timestamps in queries; the `status` column is reporting-only.
- **Repo lists** (`repo_lists`/`repo_list_items`, queries in `src/lib/lists.ts`, mutations in `src/app/actions/lists.ts`): link-shareable curated pages. Slugs carry a random suffix so lists aren't enumerable; contributions are open to any signed-in visitor until the owner closes them. List items may only reference repos already in `repos` — accepting an arbitrary GitHub URL here would create a listing that bypassed `postRepo`'s owner/org check.
- **Repo identification** (`src/lib/resolve-repo.ts`, model client in `src/lib/nemotron.ts`): turns a post's caption, OCR text or Whisper transcript into a GitHub repo, using NVIDIA Nemotron on Nebius Token Factory. The invariant is **the model proposes, GitHub decides** — every candidate is checked with `fetchPublicRepo` and a candidate that 404s is discarded regardless of the model's stated confidence, so the resolver can return "I don't know" but cannot invent a repository. Flag any change that returns a repo the GitHub check did not confirm, that lets the model's confidence substitute for validation, or that adds a `force`/override path to the ladder. `resolveRepo` takes `lookup` and `complete` as injected functions so the ladder is testable with no key and no network; keep it that way. Public endpoint `/api/identify` spends real credits, so its per-visitor **and** global ceilings are load-bearing — do not remove either, and do not persist the rate-limit key (that is what keeps /privacy's "IP never written to our database" true). A failed model call must degrade, never throw: `resolveRepo` catches it, sets `modelUnavailable`, and carries on, so an exhausted balance answers 200 with `degraded: true` instead of 502. Flag any change that lets a model error propagate as a request failure, or that drops the `degraded` flag from the response — the page branches on it to tell a visitor the truth about what just ran. **Nemotron is a reasoning model and bills its thinking against `max_tokens`**, so a budget spent entirely on reasoning returns `finish_reason: "stop"` with empty `content` — indistinguishable from "found nothing" unless `truncated` is checked. Do not lower the per-tier `max_tokens` defaults in `complete()` as an optimisation, and do not drop `truncated` from `Completion`. The tier ids are chosen by **measured latency, not parameter count** (the 30B Nano answers in 25-34s, the 550B Ultra in under a second — see the README table); flag a change that swaps in a smaller model on the assumption it is faster. `extractJson` tries every balanced object and lets the schema arbitrate, because a model that leaks its chain of thought into `content` opens braces before it answers — do not narrow it back to the first match. **Two measured guards sit in front of the GitHub check and both are load-bearing:** `isGrounded` refuses a model candidate whose name appears nowhere in the post (without it, `described_only` returned a *real but wrong* repository 14.6% of the time — validation proves existence, not correctness), and the search rung is gated on `!namePresent` — it runs only when no *grounded candidate was proposed* (without that gate `screen` went to **10.5% wrong**, because search always returns something and the ranking always picks one, so a half-read name becomes a confident near-miss). **Rung 5 (`VERIFY_SYSTEM`) is the only rung that can say no**, and it exists because the search rung's measured unresolved rate was 0%: it compares the post against the candidate's *real* GitHub description and vetoes a near-miss, which took `described_only` from 34.1% wrong to 13.3%. An absent or unparseable verdict must count as rejection, never approval — the rung's fault is over-confidence. But a verification call that *throws* must degrade, not reject: the candidate survives at confidence 0.4 with `needsReview`, because an outage must not read as "no such project". Everything the search rung returns carries `needsReview: true` and must never be auto-catalogued. Flag any change that removes either guard, that lets rung 4 run after a grounded candidate was proposed, or that treats "the rungs above failed" as equivalent to "the post named nothing" — unresolved routes to the review queue, which is the correct answer, and a wrong repository filed against a saved post is worse than none.
- **Env vars:** see `.env.example`. `TOKEN_ENCRYPTION_KEY` encrypts GitHub tokens at rest (AES-256-GCM in `src/lib/crypto.ts`).

## SEO & crawlability

- **Canonical origin comes from `src/lib/site.ts`** (`SITE_URL`, `abs()`, `NOINDEX`). Never re-derive it from `NEXT_PUBLIC_APP_URL` in a component — two sources of truth is how `canonical` and `og:url` drift apart. `SITE_URL` is already trailing-slash-stripped, so `abs("/x")` is always safe.
- **No repo list is ever indexed, and none belongs in the sitemap.** `repo_lists.visibility` is only ever `unlisted` or `private` — there is no public value — and slugs carry a random suffix precisely so lists are not enumerable. An owner sharing a link has not asked to be published, so `/lists` is in the robots.txt disallow list *and* every list page returns `robots: NOINDEX`, including the private and not-found branches. robots.txt stops crawling; the meta tag is what stops indexing of a URL a crawler found elsewhere. Both are needed — do not drop one as redundant.
- **`/repos/[id]` is the only page meant to rank**, so it is the one with derived metadata (`generateMetadata`) plus `SoftwareSourceCode` + `BreadcrumbList` JSON-LD. A `hidden` repo gets `noindex`: moderation hiding something while Google keeps serving it is the outcome to avoid. 59 of 73 repos are currently `hidden`, so reviewing that queue is the largest available increase in indexable pages — a moderation decision, not an SEO one.
- **`repos.id` is a uuid column, so `/repos/<not-a-uuid>` used to 500.** `isUuid` now gates it to a 404 before the query. Keep that guard: Googlebot slows its crawl of an entire origin in response to 5xx, and crawlers generate malformed URLs constantly. The same applies to any future route that compares a path segment against a uuid column.
- **JSON-LD never asserts what the database does not hold** (`src/lib/schema.ts`, pure and unit-tested so identity is passed in rather than read from `server-only` `@/lib/legal`). `author` is omitted because the `repos` table does not record whether a GitHub owner is a user or an organisation, and schema.org requires picking one; star counts are not expressed as an `aggregateRating`, because stars are not ratings and dressing them up as one earns a structured-data manual action. `organizationSchema` emits `legalName` only when `LEGAL_ENTITY_NAME` is set — the same rule the policy pages follow, for the same reason. Flag any change that fabricates a schema property.
- **`Organization` is emitted by the root layout, `WebSite` only by the home page.** An engine reading a single `/repos/[id]` page in isolation has no other statement of who publishes it, and the publisher is equally true on every route, so it belongs in the layout — which already reads a cookie and is therefore already dynamic, making it free. `WebSite` stays on the home page because it carries `dateModified`, which is `max(created_at)` and costs a query: moving it to the layout would either run that query on every route or publish the site's freshness without it. An audit that reports "no WebSite schema" on a repo page is describing that split, not a bug — do not satisfy it by duplicating the node sitewide.
- **`sameAs` carries only URLs that resolve, and `APP_STORE_URL` is currently the only one.** It is derived from `ascAppId` in `mobile/eas.json` rather than typed from memory, and it was checked for a 200 before being used. Every other `sameAs` an SEO audit asks for (Wikipedia, Wikidata, LinkedIn, Crunchbase) would be a machine-readable claim to own a page that does not exist — the same lie as an invented `legalName`, so an empty list omits the property. The landing page's platform rows are the matching human-readable claim: a row saying "In review" after a store has approved the build is a false statement on the most-read page on the site, so **the chip and the store link move in the same commit as the approval**.
- **`serializeJsonLd` escapes `<` to `\u003c`.** Repo names and descriptions come from GitHub, land inside a `<script>` element, and `</script>` in a description would otherwise break out of it. `JSON.stringify` alone is not sufficient here.
- **AI crawlers are deliberately not blocked.** This site ships an MCP server and a plugin, so agent readability is part of the product, and blocking a search-citation crawler removes the site from that engine's answers. To refuse model *training* while keeping citability, the tokens are `GPTBot`, `ClaudeBot`, `Bytespider`, `CCBot` and `Google-Extended` — none of which affects `Googlebot`, `OAI-SearchBot` or `Claude-SearchBot`. Do not conflate the training bot with the search bot for the same vendor.
- **The sitemap omits `priority` and `changefreq`** (Google ignores both) and gives static pages no `lastmod` at all rather than the build time — a uniform `lastmod` across every entry is what teaches Google to disregard the field site-wide. Repo entries use `lastSyncedAt ?? createdAt`, which is genuinely when the page's content last changed. It revalidates hourly and degrades to the static section if the database is unreachable, so a DB blip cannot turn the sitemap into a 5xx.
- **`/feed.xml` is the freshness signal, and `src/lib/xml.ts` is why it is a separate module.** Repo names and descriptions come from GitHub and land in XML text nodes, so `xmlText` is the RSS-shaped twin of `serializeJsonLd` — and it *strips* C0 control characters rather than escaping them, because XML 1.0 cannot represent them at all, not even as a numeric reference, so one would make the whole document unparseable for every reader. It lives in `src/lib/xml.ts` so that rule is unit-tested without a request or a database. The route mirrors `sitemap.ts` otherwise: hourly revalidation, `status = "active"` only, and a try/catch that degrades to an empty-but-valid channel instead of a 5xx.
- **Feed autodiscovery has to be repeated per route.** Next replaces the whole `alternates` object per segment rather than merging its fields, so any page that sets its own `canonical` and omits `types` silently drops the feed link from its `<head>`. `FEED_ALTERNATE` in `src/lib/site.ts` exists so that restatement is one import rather than a duplicated literal.
- **The homepage's `dateModified` is `max(created_at)` and must not become `max(last_synced_at)`.** The resync cron stamps every row on a schedule whether or not GitHub returned anything different, so including it makes the front page's freshness advance hourly while the page is unchanged — the same "suspiciously uniform" failure as a build-time `lastmod`, and it tells a consumer the field carries no information. Individual repo pages are the opposite case and legitimately use `lastSyncedAt`, matching their sitemap entry. The homepage also drops the claim entirely rather than emitting an `Invalid Date` when the driver hands back something unparseable.
- **`faqSchema` marks up questions that are already visible, never a set written to produce markup.** The four on `/support` are rendered from the same `FAQ` array the schema is built from; if that list goes, the schema goes with it. Google retired FAQ rich results in May 2026, so this earns nothing in a search result and is here only because answer engines still parse `FAQPage` — do not "restore" it to a Google feature, and do not add questions that are not on the page.
- **`/about` is a factual-accuracy surface, like the policy pages.** Every claim on it is already recorded in the code (credits from `src/lib/credits.ts`, the identification ladder from `src/lib/resolve-repo.ts`, the cookieless counting from `src/lib/analytics.ts`), and the operator block follows `src/lib/legal.ts` — **omitted**, with the omission stated plainly, when `LEGAL_ENTITY_NAME` is unset. An invented operator here is the same lie as one on `/privacy`.
- `public/llms.txt` is descriptive only. It must never contain text addressing an agent or instructing it — that is a finding when auditing someone else's site, and it would be one here.

## Migration gotchas (learned the hard way)

- Never edit an already-applied migration file — drizzle records it in the journal and won't re-run it; add a new migration instead.
- Never hand-write a future `when` timestamp in `drizzle/meta/_journal.json`: drizzle only applies entries whose `when` is greater than the last applied migration's `created_at`, so a future-dated entry makes every later migration get silently skipped (`drizzle-kit migrate` prints success even when it applies nothing).
- Code ships to prod on push to main; apply schema migrations to Neon before/with the push, never after.
- Pricing is DB-driven (`sponsor_plans` via `src/lib/pricing.ts`); never hardcode plan prices in UI — render them with `src/components/plan-price.tsx`.

## Legal & compliance

- Policy pages live in the `src/app/(legal)/` route group: `/privacy`, `/terms`, `/cookies`, `/refunds`. Every factual claim in them is derived from the code — **if you change what is collected, stored, charged, or refunded, update the matching page in the same commit.**
- Business identity comes from `src/lib/legal.ts`, which reads `LEGAL_ENTITY_NAME` / `LEGAL_ENTITY_ADDRESS` / `LEGAL_JURISDICTION` / `LEGAL_CONTACT_EMAIL`. Unset values make the pages **omit** the operator block — never hardcode a company name or address, and never invent one.
- View counting is first-party and cookieless (`src/lib/analytics.ts`: daily-rotating salted hash of IP+UA, IP never stored). `src/lib/analytics-consent.ts` gates it — `trackEvent` checks the opt-out at send time and honours Global Privacy Control automatically. Storage that fails to read counts as opted OUT.
- **Vercel Web Analytics runs alongside the first-party counting, and must stay behind our opt-out.** `src/components/vercel-analytics.tsx` passes a `beforeSend` that returns null when `analyticsOptedOut()` is true, checked per event rather than at mount so the switch takes effect without a reload. The SDK knows nothing about our switch, and /cookies promises opting out "stops your browser sending view events at all" — that has to hold for every measurement on the page, not just ours. Never mount `<Analytics />` directly in a layout. It is cookieless (daily-reset request hash), so the two-cookie claim on /cookies still holds, but it *does* derive a city, which our own table deliberately does not — /privacy says so explicitly and must keep saying so.
- **Visitor country is stored, nothing finer.** `requestCountry` reads `x-vercel-ip-country` and validates it to two ASCII letters (the header is attacker-supplied anywhere the edge is not terminating the request, and `ZZ` means unresolved). The edge also offers region, city, latitude and longitude — do not start reading them without changing `/privacy` and `/cookies` in the same commit, which both now state country-only explicitly. The country rides on the same event as the view, so the existing opt-out and GPC handling already cover it; keep it that way rather than adding a second measurement with its own switch.
- **Sentry is hardened, and must stay that way** (`src/lib/sentry-privacy.ts`, wired into both `src/instrumentation.ts` and `src/instrumentation-client.ts`). It strips `request.headers`/`request.cookies`, clears `user.geo` and pins `user.ip_address` to **null** — null rather than absent, because null is what stops Sentry inferring the address from the connection. This is not belt-and-braces: on Vercel every request carries `x-vercel-ip-city`/`-latitude`/`-longitude`, `sendDefaultPii` is deprecated, and from SDK v11 the `dataCollection` defaults apply and send the IP. Without this guard a major-version bump would silently start collecting precise location. `npm run test:analytics` is what fails if it regresses.
- `StorageNotice` is a notice, not a consent wall: the three cookies we set unprompted (auth session, theme, feed layout) are all consent-exempt. Do not turn it into an "Accept all" modal — both buttons are deliberately the same visual weight. It takes `priorConsentRequired` only so it can disclose the Google Analytics cookies to visitors who get them by default; inside the consent zone its text is unchanged.
- **Google Analytics runs under Consent Mode v2 with a region-conditional `analytics_storage` default** (`src/components/google-analytics.tsx`, dormant unless `NEXT_PUBLIC_GA_MEASUREMENT_ID` is set). `_ga` cookies are *not* consent-exempt under ePrivacy, so inside the EEA, UK and Crown Dependencies nothing is written until a visitor ticks the opt-in on /cookies — that is what keeps `StorageNotice` lawful there rather than merely accurate. Outside that zone analytics storage is lawful on an opt-out basis, so the default is granted and the same control switches it off. The zone is `src/lib/consent-region.ts` and **it fails closed**: a null, malformed, unknown-shaped (`ZZ`, `T1`, user-assigned) or missing country all require prior consent, so a geo lookup that fails or is spoofed can only cost measurement, never set a cookie that needed asking. `priorConsentRequired` is resolved **on the server** from `x-vercel-ip-country` in `src/app/layout.tsx` and passed down as a prop — never inferred in the browser from a timezone or locale, and never fetched, because the consent signal must be queued before gtag.js loads. `gaStorageGranted()` is the single source of truth for the signal, in precedence order: opt-out/GPC, then the visitor's explicit choice, then the regional default; the stored choice is **three-valued** (`"1"`/`"0"`/absent) because "never asked" has to resolve differently per region, and a refusal is written as `"0"` rather than by clearing the key so that opting out outside the zone does not silently revert. `analytics_storage` is the only key ever granted in any country — `ad_storage`, `ad_user_data` and `ad_personalization` stay denied permanently, which is what keeps /privacy's "no advertising or cross-site tracking identifiers" true. Order is load-bearing: `consent default` must be queued ahead of `config`, or the tag sets a cookie before the signal lands, and the default must carry the **already-resolved** value rather than being corrected by a later `consent update`. A full opt-out or GPC stops the tag loading at all. Note that a denied visitor is not "measured slightly worse": GA4 does not report cookieless consent-denied pings as users or sessions, it only feeds them to behavioural modelling, which is gated behind traffic thresholds this site does not meet.
- Marketing email must carry a working unsubscribe. `src/lib/unsubscribe.ts` signs a per-recipient token (HMAC over the user id, no expiry) and `notify.ts` sets `List-Unsubscribe` + `List-Unsubscribe-Post`. `unsubscribeUrl()` returns **null** rather than throwing when `AUTH_SECRET` is unset, so a misconfigured env degrades to an email without one-click rather than sending nothing.
- Accessibility floors that are already met — do not regress them: `--muted-foreground` clears 4.5:1 on both `--background` and `--muted` in all three dark themes, `--ring` clears 3:1, focus outlines are solid (not alpha-reduced), every `<main>` has `id="main"` for the skip link, and decorative logos beside their own text keep `alt=""` on purpose.
- Asset licences are recorded in `ATTRIBUTION.md`. Fonts are self-hosted by `next/font/google` at build time, so no request reaches Google at runtime — the cookie policy says so, keep it true.
